# Coverage readiness operations

Design and rationale: [coverage-slo-design.md](./coverage-slo-design.md).

## Endpoints and ownership

- `GET /api/v1/coverage/policy`: discovery of current policy bytes and content ID.
- `GET /api/v1/coverage/assessment?asset=USDC&chainId=1&policyId=...`:
  authenticated, existing coverage C2 metering (2 credits), no-store live report.
  Coverage does not replace pre-trade safety or principal authorization.
- `GET /api/v1/coverage/slo?hours=24` (also 168, 672): authenticated read-only
  fixed-slot statistics, existing coverage C2 metering. Storage failure is an
  error, never an empty healthy result.
- `/ops/coverage`: Ops-owner-only asset/chain matrix, 1/7/28-day windows,
  measured/expected slots, missing slots, signed availability and error budget.
- `GET /api/cron/coverage-slo`: CRON_SECRET-authenticated collection. The checked-in
  GitHub workflow invokes it at minutes 7/22/37/52. Infrastructure failure or a
  24h readiness/measurement alert marks the workflow failed. GitHub notification
  delivery depends on the owner's existing Actions settings; no external contact
  is sent a message by the code. Persistent below-target assets need coverage
  work or a separately reviewed profile, not a lower quorum.

## Enable production

1. Apply `supabase/migrations/0056_coverage_slo.sql` before enabling collection.
   It is additive, enables RLS, and grants the service role only SELECT/INSERT.
   Summary RPC access is service-role only. Application retries use DO NOTHING.
2. Provision `COVERAGE_SIGNER_PRIVATE_KEY` in the server environment using the
   normal secret-management process. Do not use the sample key. No key is checked
   in or generated by this feature. Missing key yields an unsigned diagnostic
   report; the SDK refuses it for execution.
3. Distribute the signer address, key validity interval, revocation status and
   policy ID to consumers independently. The reviewed reference is checked in at
   `protocol/coverage/trust/production-v1.json` and mirrored for discovery at
   `/.well-known/insight-coverage-trust.v1.json`. The proof, hosted mirror and
   policy discovery endpoint are not themselves a trust root: consumers must pin
   the reviewed bytes or signer address through their own authenticated deployment
   configuration. Key rotation needs an updated consumer trust list; revoked and
   ambiguous keys fail closed.
4. Deploy through the repository's normal validated mainline CI gate. Set the
   GitHub Actions `CRON_SECRET` to the deployed server's existing cron credential.
   Run Coverage SLO manually once and check `/ops/coverage`. Enrollment begins
   on first collection; previous history is never fabricated. First full slot
   starts after enrollment and only completed slots enter the denominator.
5. Opt execution consumers in with pinned coverage options. An API upgrade alone
   does not activate the gate for existing integrations. No partner acceptance
   or activation is implied.

## SDK integration

```ts
import { InsightGuard, STRICT_COVERAGE_POLICY, coveragePolicyId } from 'oracle-insight-guard';

// These key records must come from your trusted deployment configuration.
const keys = deploymentTrust.coverageKeys;
const policy = STRICT_COVERAGE_POLICY;
const pin = (asset: string) => ({
  asset,
  evidenceChainId: 1,
  policy,
  policyId: coveragePolicyId(policy),
  keys,
});
const guard = new InsightGuard({
  apiKey: process.env.INSIGHT_API_KEY!,
  coverage: { source: pin('ETH'), destination: pin('USDC') },
});
// Existing executeSwap / executeSwapWithPriorSeal requests are unchanged.
// Both fetch live coverage, verify local pins and refuse provider entry on failure.
// The PriorSeal flow binds source/destination coverage digests and caps authorization
// lifetime. Keep result.coverageReports alongside the signed authorization.
```

Coverage options apply to `executeSwap` and `executeSwapWithPriorSeal`. Read-only
`check`, `assessSwap`, and non-intervening authorization methods retain their
existing meaning; use `withVerifiedCoverage` or PriorSeal's
`buildCoverageBoundIntent` / `withCoverageBoundIntent` to compose an external
executor explicitly. Callback execution must start immediately; if your callback
queues work, revalidate at the actual signer/provider boundary. There is no claim
of on-chain enforcement or guaranteed freshness after broadcast.

The standard profile rejects observations without an explicit matching provider
chain, even when an adapter is globally available. Chain-agnostic or cross-chain
price candidates need a separately reviewed evidence profile. Source-chain data
does not establish settlement-chain execution health.

## Diagnose failures

- `UNCLASSIFIED_PROVIDER`: review ownership/upstream data, then append a new policy;
  unknown providers cannot grant themselves independence.
- `SOURCE_AGE_UNKNOWN` / `SOURCE_TIME_INVALID`: repair adapter timestamp provenance.
  Retrieval time cannot substitute for source time.
- `SOURCE_TOO_OLD`: refresh/repair the feed; report TTL cannot extend source TTL.
- `CHAIN_MISMATCH`: confirm actual provider-chain evidence. Do not substitute a
  testnet or a cross-chain candidate to make a green result.
- `INSUFFICIENT_COVERAGE` / `INSUFFICIENT_INDEPENDENCE`: inspect excluded, failed
  and classified providers. Three endpoints need not be three independent operators.
- `PRICE_DISAGREEMENT`: investigate the sources and pre-trade risk; a quorum alone
  does not establish price correctness.
- `MEASUREMENT_GAP`: inspect scheduler, cron authentication, deploy and database.
  Missing slots remain unavailable; a later successful request cannot fill them.
- Data ready but signed readiness low: inspect signer configuration and expiry.

The first result in a slot is retained across retries; the database stamps its
own insertion time and rejects historical slot writes. A task crossing the slot
boundary fails instead of relabeling stale observations. This is an application
append-only log, not a tamper-proof ledger against the database owner. Keep at
least 35 days of samples; archival/deletion is a separately privileged operator
action. Retention changes must not remove samples within the 28-day window.

## Rollback and acceptance

Disable the collector workflow and remove explicit consumer opt-in to roll back
the new runtime path. Preserve historical reports and targets. Existing receipt
schemas and partner policies are unaffected. Never weaken the pinned policy as
an emergency workaround; use a newly reviewed version where requirements differ.

Acceptance commands: `npm run sdk:test`, `npx jest src/lib/coverage/__tests__
--runInBand`, `node --test scripts/tests/coverage-slo-sql.test.mjs`, then normal
repository validation/build. PriorSeal runs `npm test` for binding regressions.
The embedded PostgreSQL tests validate real SQL and permissions, not production
multi-connection load. Synthetic signing tests do not prove real-world feed
availability or customer adoption.
