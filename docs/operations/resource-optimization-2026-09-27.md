# Insight 资源优化实施记录（2026-09-27）

用户约束：不新增付费服务，优先压缩和归档，保留全部读取能力。原始资源审计见 [资源审计](resource-audit-2026-09-27.md)。

## 已实现的代码和数据库变更

- 采集价格缓存改为每批最多 100 条写入，不返回整条记录；保留 24 小时丰富字段历史。仅合并同一批内完整字段一致的重复观察，不按价格或时间盲目删除不同证据。Chainlink/API3 的丰富实时结果仍从上游获得，省去没有可用记录的数据库缓存查询。
- 完整 feed 注册表同时供各提供商复用，保留原始符号大小写、链和来源身份；完整刷新会清除已移除提供商的旧缓存，异步旧查询不能覆盖新注册表。
- 实时评估的历史基线在数据库内按小时聚合，不受 PostgREST 1,000 行上限影响；只共享历史证据，实时特征每次重新计算。同一进程并发请求共享一次查询，缓存 60 秒，跨小时切换；失败不缓存。
- feed 健康批量更新采用集合式 SQL，保留重复探针计数与先成功、后失败的旧语义。
- 回收 5 个已由保留索引前缀覆盖的索引，添加带链条件的价格缓存查询索引。保留唯一约束、时间游标索引和必要的来源查询索引。
- 页面仅轮询实际展示的第一项价格结果所需的链上详情；没有结果和价格加载期间不启动详情请求，失败后轮询间隔延长至五分钟。
- npm 自动同步先执行无依赖的版本检查，只有发现变化才安装依赖和重建 cron bundle。
- 原生 cron 执行日志增加 30 天保留，业务执行证据既有保留规则不变。

## 无新增付费服务的历史存储

保留最近约一周的价格和小时记录在原表；较早记录按 UTC 日期、提供商、符号和链组成完整 JSON 块，使用 PostgreSQL 原生 TOAST 压缩，继续保留 120 天。公开的 90 天历史窗口和八周训练能力保持不变，原有失败记录、ID 和全部字段都保留。

迁移使用单日事务：锁定来源行，写入压缩块，核验完整内容后删除对应热数据。失败会整笔回滚；重复归档可安全执行，重试遵循原表语义：15 分钟快照忽略已有观察，小时快照更新值并保留原有身份。压缩块带 SHA-256 和记录数约束，读取导出时再次验证。0066 为冷数据重试写入补充保护：价格快照仍保留第一次观察；小时快照保留原 ID 和创建时间。近期写入直接通过，不查询归档；冷写入与迁移共用事务锁。0067 在完整核验所有压缩块后，每张表、每日只执行一次源行删除，限定时间范围和已锁定的 ID 集合，减少逐 feed 清理的 SQL 开销。归档表和统一历史视图仅授权 service_role。

历史 API 和分析/MCP 历史读取通过 0068 的分页 RPC：近期页直接使用原表索引；冷页仅展开填充该页所需的 UTC 日期；完整日期的偏移通过归档元数据跳过，无需解压所有先前日期。标量 JSON 响应支持真正的 2,000/10,000 行页，不受 PostgREST 行上限截断。覆盖率统计在数据库聚合完整观察，只返回提供商与符号汇总。结果回填使用带 UTC 日裁剪的历史视图；日报和长范围回填分别读取热数据与压缩块。训练读取热数据游标页，再逐块解压冷数据，不会在每一页重复展开全部八周历史。原表继续接收采集写入，健康检查仍读取近期原表。

历史价格读取改为完整分页，检测缺失页；避免以 1,000 行响应冒充长历史。压缩导出游标一直读取到空页，不依赖短页长度推断历史已结束。

生产样本压缩试验：19,458 条价格记录完整 JSON 文本约 7.86 MB，压缩后存储约 1.05 MB；5,112 条小时记录文本约 1.84 MB，压缩后约 0.34 MB。这是样本测量，不能直接当作全库已实现节省比例。按当前采集密度外推的 120 天稳态容量会在上线后用实际归档数据重新计算。

## 验证与发布顺序

1. PostgreSQL 兼容真实 SQL 测试验证健康更新语义、超过 1,000 条的基线聚合、归档逐字段一致、失败探针保留、幂等重放、删除失败回滚和权限隔离。
2. 应用测试、训练语义测试、类型检查、静态检查、生成 bundle 一致性、SDK 与浏览器烟测。
3. 先应用兼容性迁移 0063、0064；此时不会归档或删除历史。
4. 发布兼容读取代码并确认生产部署 SHA、健康状态及历史读取。
5. 初始冷数据迁移逐日核验；最终应用 0065，启用每小时最多一个 UTC 日期的维护与日志保留。
6. 区分逻辑压缩与物理空间回收：普通 DELETE 不会立即缩小表文件。物理回收必须在归档核验之后单独检查运行影响。

不削减采集频率、备用调度、安全检查、来源验证或签名职责。实际总 I/O 收益需要覆盖至少完整采集和维护周期后测量，不能把请求数下降直接等同于磁盘 I/O 同比下降。

## 生产核验结果

2026-09-27（北京时间）完成 88 个 UTC 日期的事务归档，逐日记录迁移前计数、归档计数和原表剩余数：392,274 条价格记录与 202,085 条小时记录，共 594,359 条。冷日期原表剩余均为零；完整字段、失败记录和读取能力保留。归档占用 46,759,936 字节，其中压缩载荷 38,318,548 字节，其余为元数据、索引和 TOAST 页面开销。

核验后分别完成两张原表的 `VACUUM FULL ANALYZE`，回收数据库文件空间：

| 测量阶段               |                 数据库实际大小 |
| ---------------------- | -----------------------------: |
| 最初审计               | 413,093,011 字节（393.96 MiB） |
| 索引调整后、归档前     | 399,920,275 字节（381.39 MiB） |
| 冷记录归档、物理回收后 | 235,728,019 字节（224.81 MiB） |

相对初次审计减少 177,364,992 字节，约 169.15 MiB / 42.94%。价格热表及索引约 47.98 MiB，小时热表及索引约 14.09 MiB。此处是同日实际测量，采集持续运行，并非停止业务后的静态体积。

生产读验证：跨 90 天范围的近期页与纯冷页均真实返回 2,000 条；指定 feed 完整价格读取 1,295 条，与数据库完整计数一致；单个冷日期日报读取 4,034 条，与小时完整计数一致；90 天覆盖率汇总返回 187 组、约 15.6 KB，避免传输所有小时记录。外部验证端到端耗时分别约 2.1 秒、2.2 秒、0.4 秒、3.2 秒和 4.8 秒，包含跨区域网络与代理时间，不能当作纯 SQL 执行时间。公开 readiness 返回 HTTP 200；归档完成后的新采集工作流成功。

容量推算：最近完整日期约 27,000 条价格观察、6,790 条小时观察。当前压缩载荷约 61.94 / 69.39 字节每条，归档额外页面开销约 367 字节每块。若采集规模、压缩率和其他业务表大小维持当前水平，按 113 个冷日期、最多约八个热日期估算，120 天稳态总库约 440 MiB，低于原始未压缩约 1.28 GiB 的推算。该结果是容量规划估计，新增 feeds、更多业务流量、压缩率变化和表膨胀都可能使其增大，不能承诺免费容量永远足够。

最终代码验证：应用 2,196 项测试、29 项可靠性测试、183 项 SDK 测试通过；另有 40 项训练语义测试在本次完整优化第一阶段通过。SQL 差分测试覆盖冷热混合、部分 UTC 日期、深偏移、失败记录、链/来源过滤、完整覆盖率、10,001 条结果和权限隔离；归档回滚、重放、原有身份与逐字段一致测试通过。生产预算余额不在现有指标内，因此不把物理容量下降表述为突发 I/O 余额已恢复。
