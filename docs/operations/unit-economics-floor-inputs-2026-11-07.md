# 完整单位经济地板：成本侧取数（2026-11-07）

本文件只采集成本侧输入与口径，**不修改定价公式**。当前 `4861`（micro-USDC，
`$0.004861`）是 BNB 结算通道的 **50% 毛利结算成本地板**，不是完整单位经济
地板。要判断"健康毛利"，还缺上游数据成本、价格波动缓冲、失败重试放大和基础
设施固定成本分摊四项。

所有实测数字窗口：`2026-10-08T00:00:00Z` → 采集时刻 `2026-11-07T13:00Z`，来源
生产 Supabase `public.price_snapshots` 与 `public.credit_ledger`。只读查询，无
写入。下文区分三种状态：**已实测**、**可推导（有假设）**、**缺数据**。

## 0. 先说结论

| 输入 | 状态 | 一句话 |
| --- | --- | --- |
| ① 上游数据成本（P95） | 部分实测 | 上游读取**时延 P95** 已实测；**每次读取的美元单价与按请求分摊**缺数据 |
| ② 价格波动缓冲 | 可推导（有假设） | 已实测 15m/1h 价格波动 P95；结算窗口与 gas 暴露量缺数据 |
| ③ 失败重试放大 | 可推导（有假设） | 已实测最终失败率 0.095%；逐次尝试次数无埋点，只能给区间 |
| ④ 基础设施固定成本分摊 | 缺数据 | 无月度账单、无全量请求计数；只有 30 天 93 笔**计费**调用 |

在 ①③④ 补齐前，不能对外声称"完整单位经济地板"，也不应把下面的数字当成
最终地板系数。

## 1. ① 上游数据成本（P95 而非均值）

### 口径

目标量不是"上游读取时延"，而是**一次对外调用所触发的上游读取总成本**：

```
upstreamCost(request) = Σ over providers ( unitCost(provider) × attempts(provider) )
上游成本 P95 = P95( upstreamCost(request) )   // 按请求取分位数，不取月度均值
```

之所以用 P95：均值会掩盖多头扇出（一次请求同时读多个预言机）、重试和尾部
慢 provider；拿均值定地板会在尾部请求上亏钱。

### 已实测：上游读取时延与扇出

`price_snapshots` 每个采集槽（15 分钟）/provider/symbol/chain 写一行，
`latency_ms` 是该次读取时延，`is_success` 是该次读取结果。30 天共
`158,695` 行，失败 `151` 行（按采集观测计，见第 3 节）。

### 缺数据

1. **每次上游读取的美元单价**：Alchemy/Helius 等 RPC 账单按 compute unit /
   credit 计费，不在仓库里。需要当月账单 + 各 provider 的计费单位说明。
2. **按请求的上游读取分布**：需要给对外请求路径加"本次调用了哪些 provider、
   各尝试几次"的埋点（或从现有网关日志按请求 ID 聚合）。
3. **采集任务与线上读的区分**：`price_snapshots` 只覆盖采集任务。线上 API
   可能命中缓存、可能实时读，二者成本不同，需要按路径拆分。

补齐后，就把"provider 单价 × 请求级扇出与尝试数"按请求求和，再取 P95，而
不是把上面的时延 P95 当成成本 P95。

## 2. ② 价格波动缓冲

### 口径

结算通道要求报价币种数量在"报价 → 结算"窗口内不因价格波动而低于成本。缓冲
系数按结算窗口内的绝对价格变动 P95 取：

```
volatilityBuffer = |price(t + settlementWindow) / price(t) - 1| 的 P95 × 结算暴露额
```

### 已实测：价格变动分布

同一 provider/symbol/chain 连续观测的绝对变动百分比（剔除失败与零价）：

| 窗口 | samples | p50 | **p95** | p99 |
| --- | ---: | ---: | ---: | ---: |
| 15 分钟 | 149,304 | 0.0499% | **0.6012%** | 1.179% |
| 1 小时 | 140,798 | 0.1602% | **1.2618%** | 2.7122% |

### 可推导（有假设）：缓冲金额

以 BNB 结算通道为例：`4861` 是 50% 毛利地板，对应结算成本约
`$0.004861 × 50% = $0.0024305/笔`。若结算窗口不超过 15 分钟，P95 缓冲约为
`0.6012% × $0.0024305 ≈ $0.0000146/笔`；按 1 小时 P95 则约
`$0.0000307/笔`；按 1 小时 P99 约 `$0.0000659/笔`。

这三个数字都远小于 `$0.004861` 地板本身，说明**在 BNB gas 口径下，价格波动
不是地板的主要组成部分**。但若未来把"报价币种数量"作为应收资产、或结算资产
不是稳定币，暴露额会变成整笔应收，结论会变。

### 缺数据

1. **真实报价 → 结算窗口分布**：需要 x402 结算记录里的
   `授权时间 / 结算时间`（或链上 tx 时间）分位数，而不是用 15m/1h 近似。
2. **每笔结算的 gas 暴露**：需要链上 gas used × gas price 的月度实测，而不是
  从 4861 反推。
3. **结算资产价格序列**：若结算不是 USDC 计价，需要该资产的同窗口价格。
4. 上面 15m/1h 的观测是**采集槽粒度**，不是真实结算粒度；只能作为上限近似。

## 3. ③ 失败重试的期望放大系数

### 口径

```
retryAmplification = E[ attempts per successful upstream read ]
```

`ORACLE_RETRY_PRESETS`（`src/lib/oracles/utils/retry.ts`）当前为：

| preset | maxAttempts | baseDelay | maxDelay | per-attempt timeout | 用途 |
| --- | ---: | ---: | ---: | ---: | --- |
| fast | 2 | 200 ms | 1,000 ms | 5 s | 轻量读 |
| standard（默认） | 3 | 1,000 ms | 10,000 ms | 15 s | 默认 |
| aggressive | 5 | 500 ms | 30,000 ms | 30 s | 重试敏感路径 |

### 已实测：最终失败率

`price_snapshots` 30 天：`151 / 158,695 = 0.0952%` 的观测最终失败。但一行是
**重试结束后的最终结果**，不是逐次尝试，所以不能直接得到尝试级失败率。

### 可推导（有假设）：区间而非点值

在 standard（3 次尝试）且只对失败重试、各次独立的前提下：

- 最终失败率 = 尝试失败率³ ⇒ 尝试级失败率 ≈ `0.0983`
- `E[attempts] = 1 + p + p² ≈ 1.108`

若失败几乎不触发重试（把最终失败率近似当成尝试级失败率）：

- `E[attempts] = 1 + 2 × 0.000952 ≈ 1.0019`

因此 standard 预设下的放大系数只能给出 **约 1.002–1.108** 的区间。fast
（2 次）约为 1.001–1.031；aggressive（5 次）按同一反推会得到不合理的 1.33，
说明"最终失败率反推尝试失败率"这个假设在 5 次重试下不成立，不能用于
aggressive。

### 缺数据

1. **逐次尝试埋点**：每次 retry 记录 `attempt`, `provider`, `outcome`,
   `errorClass`；或用增强重试的日志按请求聚合落库。没有它就没有点值。
2. **按 provider/路径拆分**：redstone 的 73.31% 成功率与 chainlink 的 99.98%
   差了两个数量级，混在一起取平均会系统性低估重试成本。
3. **重试是否计费**：RPC 失败请求是否计 compute unit，需账单侧确认；若失败
   不计费，成本放大应只乘成功尝试，而不是所有尝试。

## 4. ④ 基础设施固定成本分摊

### 口径

```
infraPerCall = 月度固定成本（USD） / 月度可分摊请求数
```

可分摊请求数必须包含**所有**付费与非付费路径的调用，否则分母偏小、分摊偏高。

### 已实测：计费调用量

`credit_ledger` 中 `kind='usage'` 的调用数：

| 窗口 | 计费 usage 行 |
| --- | ---: |
| 最近 30 天（2026-10-08 起） | **93** |
| 历史累计 | 2,103 |

`93` 只是**计费**调用，不含：未计费的 MCP/免费调用、entitlement 覆盖调用、
网站/文档访问、采集任务自身、被重试的上游读取。拿它做分母会把单次分摊放大
到失真。

### 缺数据

1. **月度固定成本账单**：Vercel、Supabase、Turso、Alchemy/Helius RPC、监控/
   日志等各供应商的月度金额。仓库里没有任何账单数据。
2. **全量请求计数**：数据库没有 `api_requests` / `api_request_logs` 表（已探测
   均 404）。需要从 Vercel 日志/分析导出，或在网关加按月计数器。
3. **分摊驱动（allocation driver）**：按请求数、按 CPU 秒、按存储/带宽？不同
   基础设施的成本驱动不同（例如 Supabase 按存储/IO，Vercel 按函数调用/带宽），
   单一"按调用数"可能不成立，需要分别取驱动量。
4. **采集任务成本归属**：采集任务 15 分钟一轮，30 天写入约 158,700 行
   （约 5,300 行/天），是上游读取和存储的主要来源之一；它属于"产品数据成本"
   还是"公共基础设施"，会影响分母和分子，需要先定口径。

## 5. 复算方法（数据齐了之后）

1. 上游：按请求聚合 provider 扇出与尝试数，乘各 provider 单价，取请求级 P95。
2. 波动：用真实结算窗口分布重算价格变动 P95，乘真实结算暴露额（gas 实测）。
3. 重试：用逐次尝试埋点算 `E[attempts]`，按 provider/路径分别乘到上游成本。
4. 基础设施：按供应商账单金额与其对应驱动量分摊，分母用全量请求计数。
5. 四项相加后与结算地板 `4861` 比较；只有四项都齐了，才能说"完整单位经济
   地板"和"健康毛利"。
